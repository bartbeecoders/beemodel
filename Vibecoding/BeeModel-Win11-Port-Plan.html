BeeModel on Windows 11

BeeModel is x86-64 assembly that talks to Linux through raw syscalls and to the compositor through its own Wayland client. Windows 11 runs on the same CPU, so the computation carries over unchanged: geometry, physics, the rasterizer and path tracer, BeeScript, and the file parsers. Everything that touches the OS has to be rewritten. This plan first puts the OS behind a platform layer on Linux, then writes a Windows version of that layer, developed on Omarchy with Wine and checked in a Windows 11 VM.

Goals

One .exe

A single beemodel.exe that links only Windows system DLLs (kernel32, user32, gdi32, ws2_32) and no C runtime. That is the closest Windows gets to "links nothing", because Windows has no stable syscall interface.

Same program

The same source files, the same .bee files, the same BeeScript. Only the platform layer differs. Linux behaviour does not change, and the Linux test suite stays the reference.

GPU too

The beemodel-gpu helper links vulkan-1.dll, which the NVIDIA, AMD and Intel Windows drivers provide. The CPU fallback stays as it is.
Not in scope. ARM64 Windows: the code is x86-64 assembly. The omarchy-plugin/ integration. Windows 10: it may work, but it is not tested.

The platform layer

The design decision behind W1, settled in W1a.

Linux is the interface

A plat_* routine takes the Linux syscall's arguments in the Linux syscall's registers (rdi, rsi, rdx, r10, r8, r9), with Linux flags and structures, and returns rax as the result or -errno. It keeps every register but rax, rcx and r11, as syscall does. So a call site changes from mov eax, SYS_X + syscall to call plat_x and nothing else, and the Linux version is three instructions.

The Windows version keeps the same contract and translates: it saves the registers Windows may clobber, aligns the stack, calls kernel32, and maps the result and the error. No call site has to know which system it runs on.

Converted by a checked script

Sites are rewritten by a converter that only touches straight-line mov eax, N … syscall pairs. It flags a site for hand work when a label sits between the two, when eax is used between them, or when the function keeps data in the red zone below rsp, because a call writes there. The converted binary is smaller (each site saves 2 bytes).

One class needs care: code that unmaps its own stack and then exits (none so far) cannot ret from plat_munmap.

Commit on fault. Linux reserves the 16 GiB frame arena and the other noreserve ranges and backs a page on first touch. Windows MEM_RESERVE pages fault, and MEM_COMMIT of 16 GiB counts against the commit limit. plat_mmap on Windows reserves the range and records it, and a vectored exception handler commits the touched 64 KiB chunk and resumes. That keeps every caller unchanged. Partial munmap becomes MEM_DECOMMIT; only a whole recorded range is released.

Calling convention. Internal code keeps the System V convention. Only the boundary changes: calls into Windows use rcx/rdx/r8/r9 with 32 bytes of shadow space, a 16-byte-aligned stack, and xmm6–15 preserved. The WndProc, thread entry points and the exception handler arrive in the Windows convention and need small thunks that switch back.

Working from Omarchy

There is no Windows machine. Everything is built on Linux; Wine runs the fast loop and a VM gives the real answer.

Build

sudo pacman -S mingw-w64-binutils gives x86_64-w64-mingw32-as, ld and dlltool. Import libraries for kernel32, user32, gdi32 and ws2_32 come from small .def files in the repo through dlltool, so the mingw C runtime and headers are not needed.

Daily loop: Wine

sudo pacman -S wine. Wine runs a kernel32-only executable directly, so W2 and W3 (the version, a headless render, a BeeScript run, golden images) can be scripted and run next to the Linux suite. Wine is not Windows: anything it passes is checked in the VM before a step closes.

The real check: a Windows 11 VM

omarchy-windows-vm install runs Windows 11 in KVM through dockur/windows (this machine has 32 threads, 61 GB and /dev/kvm). It connects over RDP with omarchy-windows-vm launch, and ~/Windows is shared into the guest as a network folder. Builds are copied there and run in the guest.

Running tests in the VM. The VM's compose file only forwards RDP (3389) and the web console (8006), so no SSH. The plan instead: a small runner in the guest, started as a scheduled task at log-in, watches ~/Windows/bee-run/ for a job file, runs it, and writes the output and exit code back. A Linux script drops the job and waits. That makes the Windows smoke tests scriptable from Omarchy without changing the VM's network. The VM is needed from W3's exit on; W4 (window, pen, DPI) is checked by hand over RDP.

Phases

W1 is useful on Linux even if the port stops there. W2–W7 are the port itself. W0 is an optional side check.

Groundwork on Linux
W1refactor

The platform layer Linux only started

src/plat_linux.s holds every OS call as a plat_* routine with the contract above. It goes family by family, one commit each, with the full suite green each time:

  • W1a memory: mmap, munmap, mprotect, mremap, mincore, madvise (209 sites in 62 files; the GPU helper links the layer too). done
  • W1b files and directories: read, write, pwrite64, open, openat, close, stat, fstat, newfstatat, access, fcntl, ftruncate, getdents64, chdir, rename, mkdir, rmdir, unlink, symlink, readlink, chmod, statfs (156 sites, all converted by the script; several files define their own SYS_* names, which it resolves). read, write and close also act on sockets and pipes, so the Windows version will look up what kind of handle a small int stands for. 127 syscall sites are left. done
  • W1c threads, futexes, time, the key-repeat timer. clone cannot be a plain wrapper: the new thread would return from it on its fresh stack. It becomes plat_thread_start (entry, argument, stack top, an optional tid word), which matches CreateThread on Windows anyway; both clone sites in jobs.s call it. The background job thread relies on CLONE_CHILD_CLEARTID: the kernel clears bg_tid and wakes it when the thread ends. The Windows thread wrapper will do the same clear and WakeByAddressAll after the entry returns. The other 24 sites (futex, gettid, sched_getaffinity, clock_gettime, nanosleep, time, timerfd_create, timerfd_settime) went through the script. 99 syscall sites are left. done
  • W1d child processes: the six fork + execve sites (aiproc, blend, gpu, library, video, refset) become one plat_spawn (path, argv, envp, the child's stdin/stdout/stderr), because Windows has no fork. This is the one step that changes call sites by hand.
  • W1e sockets, shared memory and poll.
  • W1f start-up (plat_init fills argv and envp; /proc/self/exe becomes plat_self_path), the window and event-loop interface (plat_win_*, plat_wait) so wayland.s becomes the Linux version of it, and a CI check that keeps syscall out of everything but plat_linux.s.
Exit: the full test suite passes, the binary is the same size within 1%, and syscall appears only in the platform file.
The port
W2build

Toolchain and a first .exe

mingw-w64 binutils reads the same Intel-syntax source and writes a PE executable. A Windows target in scripts/build.sh (--defsym WIN64=1, which drops the ELF-only sections), .def files and dlltool for the import libraries, and src/plat_win.s with the entry point, the exit, the console output and the calling-convention thunks. Everything not yet ported returns -ENOSYS.

Exit: beemodel.exe --version prints the version under Wine and in the VM, built on Linux.
W3headless

Memory, files, threads

The Windows versions of memory (commit on fault, mremap by reserving ahead, executable pages for the JIT), files and directories with UTF-16 paths, threads and WaitOnAddress, and time. Config moves to %APPDATA%\BeeModel, the cache to %LOCALAPPDATA%\BeeModel. Fonts look in C:\Windows\Fonts (Segoe UI, Consolas, Arial).

Exit: a headless render of a test scene and a BeeScript run give the same pixels and output as on Linux, under Wine and in the VM.
W4window

Window, input, clipboard

A Win32 window showing the XRGB buffer with StretchDIBits. WM_NCHITTEST drives moving and resizing through the self-drawn frame. Per-monitor DPI awareness. Keys arrive as scancodes, mapped to the evdev codes the app uses, and text arrives from WM_CHAR. Mouse look through raw input and ClipCursor. Pen pressure and tilt from WM_POINTER. Clipboard text, and files dropped on the window.

Exit: model, navigate, copy and paste between BeeModel and Notepad, at 100% and 150% scaling, in the VM over RDP. Pen input waits for real hardware.
W5loop

The event loop

plat_wait on Windows: MsgWaitForMultipleObjects over the window's message queue, waitable timers, child pipe handles, and Winsock events from WSAEventSelect. Key repeat, the job UI, live shading and playback all run from it, as they do from poll on Linux.

Exit: idle CPU near 0%, playback at the Linux frame rate, and no lag while a child process streams output.
W6processes

Child processes, sockets, the GPU helper

plat_spawn on CreateProcessW with inherited pipe handles: the AI connections (with curl.exe, which Windows 11 ships), zstd (bundled, or a built-in decoder), ffmpeg and poppler (found on PATH, with the same "not found" messages as on Linux). The live link, the MCP server and cosync move to Winsock and named pipes. The GPU helper is ported and its IPC becomes a message-mode named pipe plus one CreateFileMapping per slot, with handles passed through DuplicateHandle.

Exit: an AI request, a zstd .blend import, a video export, a PDF reference import, a live link between Windows and Linux, and a GPU path-traced render all work. Killing the helper falls back to the CPU as it does on Linux. (The VM has no GPU passthrough: the GPU render is checked on real hardware or with a software Vulkan driver.)
W7ship

CI, signing, release release

A GitHub windows-latest job runs the Windows smoke tests. The release adds beemodel-<ver>-windows-x86_64.zip with beemodel.exe and beemodel-gpu.exe. The executables are signed. Docs: a Windows section in the README and docs/WINDOWS.md, and the CHANGELOG.

Exit: a fresh Windows 11 machine downloads the zip and runs BeeModel with no SmartScreen block and no Defender alert.
Side check
W0check

Run it through WSLg no code optional

Windows 11 runs Linux Wayland apps in normal desktop windows through WSL2 and WSLg. Inside the VM this needs nested virtualization, so it is a side check rather than the first step it was: try the static beemodel there once the VM runs, and note the result in the README as a stopgap until W7.

Exit: a written result: what works, what doesn't.

Testing

  • The full Python suite stays on Linux. It drives the binary through tools/fakewl.py, and the core it tests is the same code on both systems. It runs after every W1 step.
  • Wine smoke tests (from W2): the version, a headless render compared to the Linux image, a BeeScript run, a save and reload. They run locally next to the Linux suite.
  • VM smoke tests (from W3): the same set through the shared-folder runner, before a step closes.
  • Windows CI (W7): the same set on windows-latest.
  • Golden images: headless renders must match Linux exactly. A difference points to the platform layer, not the renderer.
  • Manual checks for what scripts can't drive: pen input, DPI changes across monitors, clipboard with other apps.

Budgets & risks

Budgets

  • W1 adds under 1% to the Linux binary and costs no measurable speed (W1a: 370 bytes smaller, W1b: 121 more, W1c: the same size, the savings lost to alignment padding)
  • Windows frame times within 10% of Linux on the same machine
  • Idle CPU near 0%

Risks

  • Antivirus. A hand-assembled executable with no C runtime looks unusual to Defender's heuristics. Sign it, and submit it to Microsoft if it is flagged.
  • SmartScreen. Unsigned downloads get a warning. A code-signing certificate is a yearly cost.
  • The event loop. Windows splits waiting across messages, handles and sockets. Getting latency and idle CPU right takes the most tuning.
  • Commit on fault. A vectored handler on every first touch of the frame arena; if it costs too much, commit ahead in bigger chunks.
  • Wine is not Windows. Wine passing is a hint, not the exit.

Open questions

  • Bundle zstd.exe, or write a decoder?
  • OLE drag and drop, or WM_DROPFILES only?
  • A Windows 11 license for the VM: dockur installs an unactivated copy, which is enough for testing.
