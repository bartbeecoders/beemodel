BeeModel on Windows 11

BeeModel is x86-64 assembly that talks to Linux through raw syscalls and to the compositor through its own Wayland client. Windows 11 runs on the same CPU, so the computation carries over unchanged: geometry, physics, the rasterizer and path tracer, BeeScript, and the file parsers. Everything that touches the OS has to be rewritten. This plan first puts the OS behind a platform layer on Linux, then writes a Windows version of that layer, developed on Omarchy with Wine and checked in a Windows 11 VM.

Goals

One .exe

A single beemodel.exe that links only Windows system DLLs (kernel32, user32, gdi32, ws2_32) and no C runtime. That is the closest Windows gets to "links nothing", because Windows has no stable syscall interface.

Same program

The same source files, the same .bee files, the same BeeScript. Only the platform layer differs. Linux behaviour does not change, and the Linux test suite stays the reference.

GPU too

The beemodel-gpu helper links vulkan-1.dll, which the NVIDIA, AMD and Intel Windows drivers provide. The CPU fallback stays as it is.
Not in scope. ARM64 Windows: the code is x86-64 assembly. The omarchy-plugin/ integration. Windows 10: it may work, but it is not tested.

The platform layer

The design decision behind W1, settled in W1a.

Linux is the interface

A plat_* routine takes the Linux syscall's arguments in the Linux syscall's registers (rdi, rsi, rdx, r10, r8, r9), with Linux flags and structures, and returns rax as the result or -errno. It keeps every register but rax, rcx and r11, as syscall does. So a call site changes from mov eax, SYS_X + syscall to call plat_x and nothing else, and the Linux version is three instructions.

The Windows version keeps the same contract and translates: it saves the registers Windows may clobber, aligns the stack, calls kernel32, and maps the result and the error. No call site has to know which system it runs on.

Converted by a checked script

Sites are rewritten by a converter that only touches straight-line mov eax, N … syscall pairs. It flags a site for hand work when a label sits between the two, when eax is used between them, or when the function keeps data in the red zone below rsp, because a call writes there. The converted binary is smaller (each site saves 2 bytes).

One class needs care: code that unmaps its own stack and then exits (none so far) cannot ret from plat_munmap.

Commit on fault. Linux reserves the 16 GiB frame arena and the other noreserve ranges and backs a page on first touch. Windows MEM_RESERVE pages fault, and MEM_COMMIT of 16 GiB counts against the commit limit. plat_mmap on Windows reserves the range and records it, and a vectored exception handler commits the touched 64 KiB chunk and resumes. That keeps every caller unchanged. Partial munmap becomes MEM_DECOMMIT; only a whole recorded range is released.

Calling convention. Internal code keeps the System V convention. Only the boundary changes: calls into Windows use rcx/rdx/r8/r9 with 32 bytes of shadow space, a 16-byte-aligned stack, and xmm6–15 preserved. The WndProc, thread entry points and the exception handler arrive in the Windows convention and need small thunks that switch back.

Working from Omarchy

There is no Windows machine. Everything is built on Linux; Wine runs the fast loop and a VM gives the real answer.

Build

Nothing to install (found in W2): Arch's own GNU ld has the PE emulation (ld -V lists i386pep) and links the ELF objects that as already writes into a PE executable. src/plat_win.s writes the import table out by hand, so there is no dlltool, .def file, mingw C runtime or header. scripts/build.sh builds build/beemodel.exe next to the Linux binary whenever ld can.

Daily loop: Wine

sudo pacman -S wine, or with no root: a rootless podman container (Debian trixie with Wine 10) and WINE="podman run --rm -v $PWD:$PWD:ro,Z -w $PWD bee-wine wine" ci/check-exe.sh, which is how W2 was checked. Wine runs a kernel32-only executable directly, so W2 and W3 (the version, a headless render, a BeeScript run, golden images) can be scripted and run next to the Linux suite. Wine is not Windows: anything it passes is checked in the VM before a step closes.

The real check: a Windows 11 VM

omarchy-windows-vm install runs Windows 11 in KVM through dockur/windows (this machine has 32 threads, 61 GB and /dev/kvm). It connects over RDP with omarchy-windows-vm launch, and ~/Windows is shared into the guest as a network folder. Builds are copied there and run in the guest.

Running tests in the VM (working since W2, Windows 11 Pro 25H2, build 26200). The VM's compose file only forwards RDP (3389) and the web console (8006), so no SSH. Instead tools/winvm/runner.ps1 runs in the guest, started hidden at every log-on by a scheduled task. It watches ~/Windows/bee-run/ (\\host.lan\Data in the guest) for a job, copies the build and the job to C:\bee-run (Windows warns before running a program from a network folder), runs it with a time limit, and writes the output and exit code back. On the host, tools/winvm-run.sh beemodel.exe --version drops the job and waits; ci/check-exe.sh uses it whenever the runner is up. Setting it up takes one command in the guest (tools/winvm/setup.ps1); after that the runner updates itself from the share. Two traps found on the way: the guest's network-file cache keeps serving a file the host overwrote, so each runner goes out under a new name and setup turns the caches off; and the guest may only read a file the host wrote 0644, so it could not delete a finished job, so the host writes the share world-writable. W4 (window, pen, DPI) is checked by hand over RDP.

Groundwork on Linux
W1refactor

The platform layer Linux only done

src/plat_linux.s holds every OS call as a plat_* routine with the contract above. It goes family by family, one commit each, with the full suite green each time:

  • W1a memory: mmap, munmap, mprotect, mremap, mincore, madvise (209 sites in 62 files; the GPU helper links the layer too). done
  • W1b files and directories: read, write, pwrite64, open, openat, close, stat, fstat, newfstatat, access, fcntl, ftruncate, getdents64, chdir, rename, mkdir, rmdir, unlink, symlink, readlink, chmod, statfs (156 sites, all converted by the script; several files define their own SYS_* names, which it resolves). read, write and close also act on sockets and pipes, so the Windows version will look up what kind of handle a small int stands for. 127 syscall sites are left. done
  • W1c threads, futexes, time, the key-repeat timer. clone cannot be a plain wrapper: the new thread would return from it on its fresh stack. It becomes plat_thread_start (entry, argument, stack top, an optional tid word), which matches CreateThread on Windows anyway; both clone sites in jobs.s call it. The background job thread relies on CLONE_CHILD_CLEARTID: the kernel clears bg_tid and wakes it when the thread ends. The Windows thread wrapper will do the same clear and WakeByAddressAll after the entry returns. The other 24 sites (futex, gettid, sched_getaffinity, clock_gettime, nanosleep, time, timerfd_create, timerfd_settime) went through the script. 99 syscall sites are left. done
  • W1d child processes: the six fork + execve sites (aiproc, blend, gpu, library, video, refset) became one plat_spawn(path, argv, envp, fd map, cwd), because Windows has no fork. The map is four dwords, what the child gets on fds 0..3: one of our fds, PS_KEEP or PS_NULL; that is STARTUPINFO's three handles plus the GPU helper's fd 3. The child gets no other fd of ours (close_range, falling back to a loop): before, only the AI child closed them, and Windows does not inherit handles unless asked. refset now opens a page's output file in the parent and passes it in the map. pipe2, wait4, kill and getpid (17 sites) went through the script. 54 syscall sites are left: sockets, poll, the Wayland connection and start-up. done
  • W1e sockets, shared memory and poll: socket, socketpair, connect, bind, listen, accept4, setsockopt, sendto, sendmsg, recvmsg, poll, memfd_create, getrandom, and exit_group with them (54 sites, all through the script). Every file but plat_linux.s is now free of syscall, and 84 local SYS_* names that nothing used any more are gone. The Wayland client still speaks its protocol over these routines; giving it a platform-neutral interface is W1f. done
  • W1f start-up: _start moved to src/plat_linux_start.s (a file of its own, because the GPU helper links plat_linux.s with the C runtime's own start). It sets envp, does the Linux-only huge-page madvise and calls bee_main(argc, argv) in main.s; on Windows the entry will build UTF-8 argv and envp from GetCommandLineW and GetEnvironmentStringsW and call the same bee_main. The three /proc/self/exe uses (aiproc, gpu, library) call plat_self_path. ci/check-binary.sh, which CI and the release run, fails on any syscall instruction outside plat_linux.s. done
  • Moved to W4/W5: a platform-neutral window and event-loop interface (plat_win_*, plat_wait) over wayland.s's 51 exported routines (done in W4a, as wnd_*). It is designed better with the Win32 side in hand than guessed at now; on Linux, wayland.s already reaches the OS only through plat_*.
Exit: the full test suite passes, the binary is the same size within 1%, and syscall appears only in the platform file. Met (2026-10-24): the text is 409 bytes smaller and the CI guard holds the line.
The port
W2build

Toolchain and a first .exe

Done differently than planned, and simpler: no mingw. The same ELF objects as the Linux binary, with src/plat_win.s in place of the two Linux platform files, go through ld's PE emulation (ld -m i386pep -T src/plat_win.ld) into build/beemodel.exe, 1.59 MB, importing eleven kernel32 routines. scripts/build.sh builds it on every run when ld can; the Linux binary does not change by a byte.

  • The image sits at a fixed 0x400000 with no relocations, as on Linux: the code uses 32-bit absolute addresses, which the default 64-bit image base above 4 GiB would break. NX on, no ASLR for now. The main thread's 16 MiB stack is committed up front, because Windows grows a stack one guard page at a time and our large frames would skip it. --gc-sections loses the ELF objects' symbols in a PE link, so the exe keeps the few unused sections the Linux link drops.
  • src/plat_win.s: win_start turns GetCommandLineW into UTF-8 argv with the Microsoft C runtime's quoting rules, and GetEnvironmentStringsW into envp, and calls bee_main. plat_write (the console, UTF-8 output), plat_exit_group, plat_self_path, plat_getpid and plat_gettid are real; the other 52 answer -ENOSYS. The WENTER/WLEAVE pair keeps the Linux contract around a Windows call: it saves rdx, rsi, rdi, r8–r10 and xmm0–xmm5, aligns the stack and leaves the shadow space.
  • ci/check-exe.sh (local CI and GitHub CI, which installs Wine): a 64-bit PE that imports only Windows system DLLs, and --version under Wine equal to the Linux binary's.

Under Wine 10, --version, --help and --list-ops (all 672 operators) print exactly what Linux prints, and quotes, backslashes and UTF-8 in arguments arrive unchanged. --eval and --selftest crash on the first allocation, as expected: memory is W3.

Exit: beemodel.exe --version prints the version under Wine and in the VM, built on Linux. Met (2026-10-25), under Wine 10 and in the Windows 11 VM: there too --version, --help and all 672 operators match Linux, quoted and UTF-8 arguments arrive unchanged, and Defender lets the unsigned exe run. --eval ends in an access violation (0xC0000005) without a crash dialog hanging the runner.
W3headless

Memory, files, threads done

The Windows versions of memory (commit on fault, mremap by reserving ahead, executable pages for the JIT), files and directories with UTF-16 paths, threads and WaitOnAddress, and time. Config moves to %APPDATA%\BeeModel, the cache to %LOCALAPPDATA%\BeeModel. Fonts look in C:\Windows\Fonts (Segoe UI, Consolas, Arial).

  • W3a memory, in plat_win.s with the Linux contract. A plain anonymous map is reserved and committed at once. A MAP_NORESERVE one (the 16 GiB frame arena, the simulation ranges) is only reserved and recorded in a table of 1024; a vectored exception handler commits the touched 64 KiB of such a range and resumes, and passes any other fault on, so a real crash stays a crash. Stacks (MAP_STACK) are committed whole: a fault on a stack has no stack to be handled on. munmap walks VirtualQuery across allocations, releases those it covers whole and decommits the rest (releasing an allocation once nothing in it is left). MADV_DONTNEED decommits and, outside the table, commits again, so the pages read zero as on Linux. mremap shrinks in place and grows by moving; mprotect is VirtualProtect (the field JIT); mincore counts committed pages as in memory. File and shared mappings stay -ENOSYS until W3b and W6. tests/win/mem.s, linked with plat_win.s into build/test-mem.exe and run by ci/check-exe.sh, checks it all in 27 lines, the contract included. With BEEMODEL_THREADS=0, beemodel.exe --selftest passes every test under Wine and on Windows 11: arenas, pools, the field JIT, the 1M-triangle cluster DAG (its timings read 0 until W3c brings the clock). done
  • W3b files and directories. An fd is an index into a table of 1024 {handle, kind, aux}; 0–2 are the standard handles, and the lowest free one is given out, as on Linux. Paths go from UTF-8 to UTF-16 (/ works as a separator as it is). open maps O_CREAT, O_EXCL and O_TRUNC to CreateFileW's dispositions and shares files for reading, writing and deleting, as Unix does; a directory opened to read becomes a listing, which getdents64 fills from FindFirstFileW/FindNextFileW as linux_dirent64 records (an entry that does not fit waits for the next call). stat, fstat and newfstatat fill the Linux struct stat (mode, size, FILETIMEs as Unix times, the file index as inode). pwrite64 and ftruncate put the file position back, since Windows moves it. A private file mapping is a copy-on-write view (FILE_MAP_COPY): mprotect makes it writable as PAGE_WRITECOPY, munmap unmaps a view whole (Windows cannot cut one, so a partly unmapped view stays until its last part goes), madvise leaves it be. Windows errors map to errno through a table. rename replaces, chmod is a no-op (the callers only make private folders), statfs gives the free space; fcntl and symlink, used only with sockets and pipes, wait for W6. tests/win/files.s (44 checks, in a folder of its own in %TEMP%) passes under Wine and on Windows 11. Under Wine, with one thread, the BeeScript suite (50 of 50), the compatibility check and the image formats test (PNG, JPEG, EXR read and written) pass against beemodel.exe; the suites that save to ~/BeeModel wait for W3d, since Windows has no HOME, and those with time budgets for W3c's clock. done
  • W3c threads, futexes and time. plat_thread_start starts a thread with CreateThread (suspended, so the tid word holds its id before it runs); on a small stack of its own the thread moves to the one it was given (a MAP_STACK mapping, committed whole) and points its TEB stack bounds (gs:[8], gs:[16]) there, as fiber and coroutine libraries do, so that exception dispatch and the stack probes inside Windows see the stack it is on; when the entry returns it puts them back, clears the tid word and wakes it (WakeByAddressAll), as CLONE_CHILD_CLEARTID does. plat_futex is WaitOnAddress (with Linux's -EAGAIN and -ETIMEDOUT) and WakeByAddressSingle/All; they live in the API set api-ms-win-core-synch-l1-2-0.dll, not kernel32, so the exe imports it and ci/check-exe.sh allows it. CLOCK_MONOTONIC comes from the performance counter, CLOCK_REALTIME from GetSystemTimePreciseAsFileTime; time, nanosleep (Sleep, rounded up to ms) and sched_getaffinity (a bit per processor) go with them. With threads came a race in W3a's commit on fault: two threads touching the same untouched 64 KiB at once, and the second one's handler found the page committed and took it for a real fault; a page committed with the range's own protection now runs the access again. tests/win/threads.s (18 checks: the clocks, futex wait, timeout and wake across threads, the tid word, 8 threads on their own stacks, and 8 threads racing into the same 64 KiB 20 times, which crashed every time before the fix) passes under Wine and on Windows 11. beemodel.exe --selftest now passes with all workers: 31 under Wine (8M elements 85 ms serial, 5 ms parallel; the 1M-triangle cluster DAG in 230 ms), 1 in the 2-CPU VM; the BeeScript suite, compat and image_io pass with threads under Wine. The key-repeat timerfd goes with poll in W5. done
  • W3d home and fonts. The Windows start gives the program the HOME it looks for: BEEMODEL_HOME (a portable home, and how tests under Wine, which drops HOME, give one), else HOME as it is (Git Bash sets it), else USERPROFILE; and XDG_RUNTIME_DIR from TEMP for W6; both with / for \, as the code splits paths at /. Changed from the plan: not %APPDATA%\BeeModel and %LOCALAPPDATA%\BeeModel but the Linux layout in the user's folder (~/BeeModel, ~/.config/beemodel, ~/.cache/beemodel), as git and ssh keep theirs: the code finds them all through home_join, and Linux does not change by a byte (honouring XDG_CONFIG_HOME there instead would have sent the tests, which set only HOME, into a desktop's real config). The UI fonts fall back to Segoe UI and Consolas (then Arial, Courier New) in C:/Windows/Fonts, after the Linux ones, and 3D text scans that folder too (fonts by file name: arialbd, times, consola each give a closed mesh on Windows 11). tests/win/env.s checks the environment. Paths typed with \, and a typed C:/... counting as absolute in the file dialog, belong to W4's UI.
Exit: a headless render of a test scene and a BeeScript run give the same pixels and output as on Linux, under Wine and in the VM. Met (2026-10-25): the studio scene of tests/product_shot.bees, path-traced at 320×180, 16 samples, all workers, is byte-identical (the same PNG, MD5 d43ac808…) from the Linux binary, from beemodel.exe under Wine and from beemodel.exe on Windows 11. Under Wine, against beemodel.exe, the Linux suites that need neither the window nor a child process pass: beescript (50), compat, image_io, sculpt_paint, billion, world, play, logic, solver, landscape, shatter, fields, lighting, enclosure, procedural, animation, materials, brep, assembly, step. Left for later: library's thumbnails (child processes, W6), viewport, mcp_schema, sculpt20m and the UI parts of text and particles (the window, W4/W6). One particles budget (a frame within 8 steps) misses under Wine only, 8 ms against 4.6: Wine's cost of waking 31 workers a frame; on Windows 11 the frame takes 2.2 steps, as on Linux.
W4window

Window, input, clipboard

First the window and event-loop interface moved here from W1: plat_win_* and plat_wait, with wayland.s as its Linux version. Then a Win32 window showing the XRGB buffer with StretchDIBits. WM_NCHITTEST drives moving and resizing through the self-drawn frame. Per-monitor DPI awareness. Keys arrive as scancodes, mapped to the evdev codes the app uses, and text arrives from WM_CHAR. Mouse look through raw input and ClipCursor. Pen pressure and tilt from WM_POINTER. Clipboard text, and files dropped on the window.

  • W4a the window interface, on Linux. wayland.s exported 51 names, and main.s, ui.s, jobui.s and play.s built Wayland requests themselves. Now the platform-neutral part is src/window.s: the window's size, scale and flags, the pen's pressure, the frame-time ring, render (the UI drawn into whatever buffer the platform gives) and the shared helpers (getenv, str_eq, fatal, mono_ns). The platform's window provides 15 routines, documented at the top of window.s: wnd_open, wnd_fd, wnd_flush, wnd_dispatch, wnd_pump (a long job keeps the window alive), wnd_ready / wnd_buffer / wnd_present (a frame), wnd_move, wnd_resize, wnd_minimize, wnd_maximize_toggle (the self-drawn title bar), wnd_lock_pointer / wnd_unlock_pointer (play mode) and set_cursor. Changed from the plan: named wnd_*, as plat_win_* reads as the Windows platform file; and no plat_wait: the main loop keeps polling, with the window as one more fd, which the Windows plat_poll answers from the message queue. The clipboard keeps its own interface (clip_copy, clip_paste). The Linux binary is the same size and its suites pass.
Exit: model, navigate, copy and paste between BeeModel and Notepad, at 100% and 150% scaling, in the VM over RDP. Pen input waits for real hardware.
W5loop

The event loop

plat_wait on Windows: MsgWaitForMultipleObjects over the window's message queue, waitable timers, child pipe handles, and Winsock events from WSAEventSelect. Key repeat, the job UI, live shading and playback all run from it, as they do from poll on Linux.

Exit: idle CPU near 0%, playback at the Linux frame rate, and no lag while a child process streams output.
W6processes

Child processes, sockets, the GPU helper

plat_spawn on CreateProcessW with inherited pipe handles: the AI connections (with curl.exe, which Windows 11 ships), zstd (bundled, or a built-in decoder), ffmpeg and poppler (found on PATH, with the same "not found" messages as on Linux). The live link, the MCP server and cosync move to Winsock and named pipes. The GPU helper is ported and its IPC becomes a message-mode named pipe plus one CreateFileMapping per slot, with handles passed through DuplicateHandle.

Exit: an AI request, a zstd .blend import, a video export, a PDF reference import, a live link between Windows and Linux, and a GPU path-traced render all work. Killing the helper falls back to the CPU as it does on Linux. (The VM has no GPU passthrough: the GPU render is checked on real hardware or with a software Vulkan driver.)

Testing

  • The full Python suite stays on Linux. It drives the binary through tools/fakewl.py, and the core it tests is the same code on both systems. It runs after every W1 step.
  • Wine smoke tests (from W2): the version, a headless render compared to the Linux image, a BeeScript run, a save and reload. They run locally next to the Linux suite. W2's part is ci/check-exe.sh, in ci/local.sh and in GitHub CI.
  • VM smoke tests (from W3): the same set through the shared-folder runner (tools/winvm-run.sh, there since W2), before a step closes.
  • Windows CI (W7): the same set on windows-latest.
  • Golden images: headless renders must match Linux exactly. A difference points to the platform layer, not the renderer.
  • Manual checks for what scripts can't drive: pen input, DPI changes across monitors, clipboard with other apps.

Budgets & risks

Budgets

  • W1 adds under 1% to the Linux binary and costs no measurable speed (W1a: 370 bytes smaller, W1b: 121 more, W1c: the same size, the savings lost to alignment padding; after W1e the text is 409 bytes smaller than on main; W2 does not change it)
  • beemodel.exe about the size of the Linux binary (W2: 1,592,320 bytes against 1,598,776)
  • Windows frame times within 10% of Linux on the same machine
  • Idle CPU near 0%

Risks

  • Antivirus. A hand-assembled executable with no C runtime looks unusual to Defender's heuristics. Sign it, and submit it to Microsoft if it is flagged.
  • SmartScreen. Unsigned downloads get a warning. A code-signing certificate is a yearly cost.
  • The event loop. Windows splits waiting across messages, handles and sockets. Getting latency and idle CPU right takes the most tuning.
  • Commit on fault. A vectored handler on every first touch of the frame arena; if it costs too much, commit ahead in bigger chunks.
  • Wine is not Windows. Wine passing is a hint, not the exit.

Open questions

  • Bundle zstd.exe, or write a decoder?
  • OLE drag and drop, or WM_DROPFILES only?
  • Console or GUI subsystem: W2 is a console program, so --version prints in a terminal, but one started from Explorer opens a console window. A GUI exe that attaches to its parent's console, or two exes, decided in W4.
  • A Windows 11 license for the VM: dockur installs an unactivated copy, which is enough for testing.
