BeeModel on Windows 11

BeeModel is x86-64 assembly that talks to Linux through raw syscalls and to the compositor through its own Wayland client. Windows 11 runs on the same CPU, so the computation carries over unchanged: geometry, physics, the rasterizer and path tracer, BeeScript, and the file parsers. Everything that touches the OS has to be rewritten. This plan starts with a zero-code check through WSLg, then puts the OS behind a platform layer, then writes a native Windows version of that layer.

BeeModel · Vibecoding/BeeModel-Win11-Port-Plan.html · Companion to the Masterplan · Written 2026-10-19 against v0.19.0

Goals

One .exe

A single beemodel.exe that links only Windows system DLLs (kernel32, user32, gdi32, ws2_32) and no C runtime. That is the closest Windows gets to "links nothing", because Windows has no stable syscall interface.

Same program

The same source files, the same .bee files, the same BeeScript. Only the platform layer differs. Linux behaviour does not change, and the Linux test suite stays the reference.

GPU too

The beemodel-gpu helper links vulkan-1.dll, which the NVIDIA, AMD and Intel Windows drivers provide. The CPU fallback stays as it is.
Not in scope. ARM64 Windows: the code is x86-64 assembly. The omarchy-plugin/ integration. Windows 10: it may work, but it is not tested.

Calling convention. Internal code keeps the System V convention. Only the boundary changes: calls into Windows use rcx/rdx/r8/r9 with 32 bytes of shadow space, a 16-byte-aligned stack, and xmm6–15 preserved. The WndProc and thread entry points arrive in the Windows convention and need small thunks that switch back.

Phases

W0 can ship on its own. W1 is useful on Linux even if the port stops there. W2–W7 are the port itself.

Check first
W0check

Run it through WSLg no code

Windows 11 runs Linux Wayland apps in normal desktop windows through WSL2 and WSLg, which are built in. Try the static beemodel there, and beemodel-gpu through Mesa's D3D12-backed Vulkan driver (it may fall back to the CPU). Measure frame times, input (mouse look, tablet), clipboard with Windows apps, and file access to /mnt/c.

If this is good enough, ship a "Windows 11 through WSL" install note in the README, and decide on W1–W7 later.

Exit: a written result: what works, what doesn't, and frame times next to native Linux on the same machine.
Groundwork on Linux
W1refactor

The platform layer Linux only

New src/plat_linux.s, with every OS call behind a plat_* routine: memory, files, directories, threads and futexes, time, processes, pipes, sockets, shared memory. The ~400 syscall sites in 69 files call it instead. Nothing changes in behaviour. A grep in CI keeps new syscall instructions out of everything except plat_linux.s.

The window and the event loop get their own interface (plat_win_*, plat_wait) so wayland.s becomes the Linux version of it.

Exit: the full test suite passes, the binary is the same size within 1%, and syscall appears only in the platform files.
The port
W2build

Toolchain and a first .exe

mingw-w64 binutils (x86_64-w64-mingw32-as/ld) reads the same Intel-syntax source and writes a Windows executable. Add import libraries for the system DLLs, a Windows target in scripts/build.sh, and src/plat_win.s with the entry point, the exit, and the calling-convention thunks.

Exit: beemodel.exe --version prints the version on Windows 11, built on Linux.
W3headless

Memory, files, threads

The Windows versions of memory (including the reserved-range replacement for mremap and executable pages for the JIT), files and directories with UTF-16 paths, threads and WaitOnAddress, and time. Config moves to %APPDATA%\BeeModel. Fonts look in C:\Windows\Fonts (Segoe UI, Consolas, Arial).

Exit: a headless render of a test scene and a BeeScript run on Windows give the same pixels and output as on Linux.
W4window

Window, input, clipboard

A Win32 window showing the XRGB buffer with StretchDIBits. WM_NCHITTEST drives moving and resizing through the self-drawn frame. Per-monitor DPI awareness. Keys arrive as scancodes, mapped to the evdev codes the app uses, and text arrives from WM_CHAR. Mouse look through raw input and ClipCursor. Pen pressure and tilt from WM_POINTER. Clipboard text, and files dropped on the window.

Exit: model, sculpt with a pen, navigate, copy and paste between BeeModel and Notepad, on a 100% and a 150% display.
W5loop

The event loop

plat_wait on Windows: MsgWaitForMultipleObjects over the window's message queue, waitable timers, child pipe handles, and Winsock events from WSAEventSelect. Key repeat, the job UI, live shading and playback all run from it, as they do from poll on Linux.

Exit: idle CPU near 0%, playback at the Linux frame rate, and no lag while a child process streams output.
W6processes

Child processes, sockets, the GPU helper

CreateProcessW with inherited pipe handles for the AI connections (with curl.exe, which Windows 11 ships) and for zstd (bundled, or a built-in decoder). The live link, the MCP server and cosync move to Winsock and named pipes. The GPU helper is ported and its IPC becomes a message-mode named pipe plus one CreateFileMapping per slot, with handles passed through DuplicateHandle.

Exit: an AI request, a zstd .blend import, a live link between Windows and Linux, and a GPU path-traced render all work. Killing the helper falls back to the CPU as it does on Linux.
W7ship

CI, signing, release release

A GitHub windows-latest job runs the Windows smoke tests. The release adds beemodel-<ver>-windows-x86_64.zip with beemodel.exe and beemodel-gpu.exe. The executables are signed. Docs: a Windows section in the README and docs/WINDOWS.md, and the CHANGELOG.

Exit: a fresh Windows 11 machine downloads the zip and runs BeeModel with no SmartScreen block and no Defender alert.

Testing

  • The full Python suite stays on Linux. It drives the binary through tools/fakewl.py, and the core it tests is the same code on both systems.
  • Windows smoke tests (W7): start, load a scene, a headless render compared to a Linux reference image, a BeeScript run, a save and reload, the GPU helper with fallback.
  • Golden images: headless renders must match Linux exactly. A difference points to the platform layer, not the renderer.
  • Manual checks for what CI can't drive: pen input, DPI changes when the window moves to another monitor, clipboard with other apps.

Budgets & risks

Budgets

  • W1 adds under 1% to the Linux binary and costs no measurable speed
  • Windows frame times within 10% of Linux on the same machine
  • Idle CPU near 0%

Risks

  • Antivirus. A hand-assembled executable with no C runtime looks unusual to Defender's heuristics. Sign it, and submit it to Microsoft if it is flagged.
  • SmartScreen. Unsigned downloads get a warning. A code-signing certificate is a yearly cost.
  • The event loop. Windows splits waiting across messages, handles and sockets. Getting latency and idle CPU right takes the most tuning.

Open questions

  • Is W0 (WSLg) good enough to make the native port optional?
  • Bundle zstd.exe, or write a decoder?
  • OLE drag and drop, or WM_DROPFILES only?
