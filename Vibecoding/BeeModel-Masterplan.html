Product & technical plan

From a 25 KB shell to a complete 3D modeling suite

How BeeModel grows from today's assembly-language Wayland shell into a full modeler. It combines Blender's polygon and sculpting workflow, a CAD tool's parametric precision, and Unreal Engine's real-time, node-driven, large-world thinking. It is AI-native from the start: every action can be driven by an agent through a built-in MCP server. Through all of it, the original rule holds: hand-written x86-64, no libraries, and performance and memory first.

BeeModel · Vibecoding/BeeModel-Masterplan.html · Target machine: Ryzen-class 16C/32T with AVX-512, RTX 4080 SUPER, Hyprland (Wayland), 3× 1080p monitors at scale 1

Vision & principles

What BeeModel is, and the rules every later decision is checked against.

North star. A professional 3D modeler that starts in under 50 ms, fits in under 2 MB, stays responsive with 100 million triangles, and that a human and an AI agent can operate together. Both use the same commands, the same undo history and the same permissions.

1 · Zero dependencies

The shipped binary links nothing: no libc, libwayland, Vulkan loader, FreeType or zlib. Every format, protocol and algorithm we need is written in assembly. Python and other dev-time code generators are allowed if they emit assembly sources that are committed to the repo.

2 · Memory is a feature

Data-oriented layouts (struct-of-arrays), arenas instead of malloc-per-object, mmap'd files and compact 32-bit indices. Every subsystem gets a memory budget, and CI fails when one is exceeded.

3 · Never block the human

The UI thread only reads snapshots. Heavy work goes to a job system on all 32 hardware threads. Every long operation can be cancelled and reports progress.

4 · One operator table

Every action is declared once, with name, parameters, types, ranges, docs and undo behaviour. From that single declaration we generate the menus, hotkeys, property panels, BeeScript bindings and MCP tools (see the operator spine).

5 · Non-destructive by default

Modifier stacks, parametric feature trees and node graphs keep the original intent editable. Destructive edits stay possible but are always journaled.

6 · Agents are first-class users

AI changes go through the same operator layer and the same undo history, and are shown as reviewable change sets. AI never gets a private back door into the data.

Who it is for

Artists

Hard-surface and organic modeling, sculpting, UVs, texture paint and quick renders. Benchmark: Blender's modeling and sculpting workflow.

Makers & engineers

Sketch → constrain → extrude, exact dimensions, fillets, assemblies, drawings and 3MF/STEP export. Benchmarks: FreeCAD, Fusion and Onshape for parts.

Technical & world builders

Procedural nodes, scattering, LODs, huge scenes and a play mode. Benchmarks: Unreal Engine's PCG, Blueprints and Nanite-style geometry.

Architecture

Layers, threads and how data flows. Each layer may call only the layers below it.

Threading model

UI / main thread

Owns the Wayland socket, input, layout and composition of the final frame. It never waits on a lock that a worker might hold. It reads immutable scene snapshots through an atomically swapped pointer: an epoch-based read-copy-update (RCU) scheme with retired generations freed in batches.

Workers (N = cores − 1)

A work-stealing job system built on clone(CLONE_VM|CLONE_THREAD…) and futex. Jobs are 64-byte descriptors in lock-free Chase–Lev deques. Long jobs check a cancellation flag every few milliseconds. Fibers let jobs wait for each other without blocking a thread.

Render threads

Viewport tiles (64×64) are shaded in parallel, with one AVX-512 lane group per 4×4 quad. The path tracer runs as a low-priority background job that keeps refining while the camera is still.

Service thread

MCP and collaboration sockets, autosave and file watching, all on epoll. Incoming commands are queued onto the operator spine and executed in order like any other user action.

The operator spine

The most important design decision. Every feature in this plan plugs into it.

Every user-visible action (extrude, add cube, set material, export, toggle pane) is an operator, declared once with assembly macros. A dev-time generator turns that table into six things:

1 · UI

Menu entries, toolbar buttons and an auto-generated "last operator" redo panel with live-editable parameters, as in Blender's F9 panel.

2 · Input

Default keymap entries, pie-menu slots and modal handlers (grab, rotate, scale with numeric input).

3 · BeeScript

A typed function binding, e.g. mesh.extrude(dist: 0.5, axis: "normal").

4 · MCP tool

A JSON Schema generated from the parameter table, with the doc string as the tool description.

5 · Undo journal

A compact binary record of the operator id and parameters, so the history can be replayed and synchronized.

6 · Docs & tests

A generated reference page, plus a fuzz target that feeds random valid parameters.
# src/ops/mesh_extrude.s  — declaration (sketch)
OPERATOR mesh_extrude, "Extrude Region", flags=UNDO|MODAL|AI_SAFE
    PARAM_F32   distance,  "Distance",  default=0.0,  min=-1e6, max=1e6, unit=LENGTH
    PARAM_ENUM  axis,      "Axis",      default=NORMAL, values=NORMAL|X|Y|Z|VIEW
    PARAM_BOOL  dissolve,  "Dissolve orthogonal edges", default=0
    POLL        poll_edit_mesh_has_faces      # when is it available?
    EXEC        exec_mesh_extrude             # pure: (doc snapshot, params) -> delta
    MODAL       modal_translate_along_axis    # interactive variant
    DOC         "Extrude selected faces along their normals."
END_OPERATOR
Why this matters. With this design, adding a feature makes it available to the AI, the script, the menu, the hotkey and the redo panel at the same time. It also means an agent can never do anything a user cannot see, undo or audit.

Data model & files

An entity-component scene, several geometry representations, and a native format built for speed and diffs.

Scene: ECS + dependency graph

  • Entities: objects, collections, lights, cameras, sketches, node groups, materials.
  • Components are stored as SoA tables per type, e.g. Transform, MeshRef, ModifierStack, FeatureTree, Material, Physics, Tags.
  • A directed acyclic dependency graph (parent → child, modifier inputs, constraints, drivers) is evaluated incrementally. Only dirty nodes are recomputed, in parallel waves.
  • Collections, layers and Unreal-style data layers let you stream parts of a scene in and out.

Geometry representations

  • Edit mesh: half-edge / BMesh-style with n-gons, loops, seams, creases and custom attributes. Used for interactive editing.
  • Render mesh: triangulated, quantized, organized into meshlets (128 triangles each). Used for display and export.
  • SDF / F-rep: implicit solids for blending and smooth booleans, meshed with dual contouring.
  • B-rep + NURBS: exact CAD solids (later phase).
  • Curves: Bézier, NURBS and 2D sketch geometry.
  • Point clouds & volumes: scatter output, scans and VDB-like sparse grids.

Native format: .bee

  • A chunked binary container: header, chunk table, then 64 KiB-aligned chunks that can be mmap'd straight into memory.
  • Each chunk is content-addressed by a hash we implement ourselves (BLAKE3). Identical chunks are stored once, and file diffs are cheap.
  • Optional per-chunk LZ4-style compression (own implementation, decompresses at about 4 GB/s per core).
  • An embedded operator journal: the file can be replayed, inspected and "time-travelled".
  • A low-resolution preview thumbnail plus a JSON metadata chunk so other tools (and AI agents) can inspect the file.
  • A forward-compatible schema: unknown chunks are preserved on save.

Import / export (all hand-written)

This needs our own inflate/deflate (glTF textures, PNG, 3MF zip), XML and JSON parsers, and a baseline JPEG decoder. Every importer is fuzzed from day one.

Rendering

CPU-first, built to use all 32 threads and AVX-512, with a GPU path that stays outside the core.

Viewport rasterizer

  • Binned, tiled triangle rasterizer: 64×64 tiles, per-tile triangle lists, multithreaded.
  • AVX-512 edge functions test 16 pixels per instruction, with a hierarchical-Z early reject.
  • A visibility buffer (triangle id + instance id), shaded in a deferred pass. Overdraw cost becomes close to zero.
  • Meshlet culling (frustum, back-face cone, occlusion against last frame's depth pyramid), as in Unreal's Nanite.
  • Modes: wireframe, solid + cavity + AO, MatCap, X-ray, material preview, CAD hidden-line, zebra stripes and curvature for surface quality checks.
  • Overlays: anti-aliased lines (Xiaolin Wu), gizmos, measurements, snapping hints.
  • Temporal anti-aliasing plus progressive refinement while the camera is still.

Path tracer ("Hive")

  • A BVH8 built in parallel with binned SAH and traversed with AVX-512 (8-wide nodes, 16-ray packets for primary rays).
  • Unidirectional path tracing with multiple importance sampling and next-event estimation. Later: ReSTIR-style resampling for many lights.
  • Principled BSDF (Disney/OpenPBR subset): metal, dielectric, clearcoat, sheen, subsurface (random walk), thin film.
  • HDRI environments with importance sampling, sun & sky model, area/spot/IES lights.
  • Our own denoiser: À-trous wavelet / SVGF guided by albedo and normal buffers; later a small learned denoiser running on our own int8/AVX-512 VNNI inference code.
  • Output: PNG, EXR (half/float, our own PIZ/zip codecs), render passes and AOVs.
GPU decision (RTX 4080 SUPER). NVIDIA's userspace driver is closed, so talking to the GPU from pure assembly would mean using undocumented ioctls. That is fragile and possibly unworkable. Plan: the core stays CPU-only and library-free. A separate, optional beemodel-gpu helper process may load Vulkan and accelerate path tracing and booleans, connected through a shared-memory ring buffer. If it is missing, everything still works. This keeps the "no libraries" rule for the product core while leaving the door open.

Polygon modeling

Blender-class editing, where every tool is an operator with an interactive (modal) variant.

Selection

  • Vertex / edge / face / object modes
  • Box, lasso, circle, paint select
  • Loop, ring, linked, shortest path
  • Select similar (normal, area, material)
  • Grow/shrink, checker deselect
  • GPU-free picking via the visibility buffer

Core tools

  • Grab / rotate / scale with axis locks and typed values ("G X 2.5 ⏎")
  • Extrude (region, individual, along normals)
  • Inset, bevel (vertex/edge, profiles)
  • Loop cut & slide, knife, bisect
  • Bridge loops, fill, grid fill, poke
  • Merge, dissolve, collapse, rip, split
  • Spin, screw, solidify, mirror

Modifier stack

  • Subdivision (Catmull–Clark, Loop) with creases
  • Mirror, array, boolean, bevel, solidify
  • Remesh (voxel, quad), decimate, weld
  • Deform: lattice, curve, displace, smooth
  • Weighted normals, edge split
  • Each modifier evaluated as a parallel job with cached results

Snapping & precision

  • Increment, vertex, edge, face, edge midpoint, perpendicular, grid
  • 3D cursor and custom pivots
  • Transform orientations (global, local, normal, view, custom)
  • Exact numeric entry with units and expressions ("=12mm*2")

Topology quality

  • Non-manifold, zero-area and flipped-normal detection with viewport highlights
  • Pole and n-gon overlays
  • Automatic mesh repair operator
  • Quad retopology tools: shrinkwrap snapping, poly-build

Robust booleans

  • Exact geometric predicates (Shewchuk-style adaptive orient3d) in assembly
  • Mesh arrangement with plane-based geometry so booleans never fail on coplanar faces
  • Fast mode (float) and exact mode (expansion arithmetic)

CAD & precision

The parametric, constraint-driven side, aimed at makers and engineers.

Sketcher + constraint solver

  • 2D sketches on planes or faces: lines, arcs, circles, splines, slots, polygons.
  • Constraints: coincident, parallel, perpendicular, tangent, equal, symmetric, horizontal/vertical, fixed, dimensions (distance, angle, radius).
  • Solver: Newton–Raphson / Levenberg–Marquardt on the constraint graph, split into independent subsystems (DR-planning).
  • Degrees-of-freedom display: under-constrained geometry is blue, fully constrained geometry is black, conflicts are red with an explanation.
  • Automatic constraint inference while drawing (snaps that become constraints).

Feature tree (parametric history)

  • Pad/extrude, pocket, revolve, sweep, loft, shell, draft, rib.
  • Fillet and chamfer (variable radius), hole wizard (ISO/ANSI threads), patterns (linear, circular, along a curve).
  • Parameters table and expressions, e.g. wall = 2mm; width = 10*wall, with design variants (configurations).
  • Rollback bar, edit any feature, and robust topological naming: persistent ids that survive upstream edits, the classic CAD pain point.

Solid kernel strategy

  • Stage 1: features evaluated on meshes plus exact booleans. Good enough for 3D printing.
  • Stage 2: an SDF/F-rep kernel for smooth blends, variable fillets and lattices (great for additive manufacturing).
  • Stage 3: a B-rep kernel with NURBS surfaces, surface–surface intersection, and STEP AP242 export. The largest single item in this plan, so it is deliberately last.

Engineering outputs

  • Units (mm, in, m), tolerances, and measurement tools (distance, angle, area, volume, mass with material density).
  • Assemblies with mates/joints and interference checks.
  • 2D drawings: orthographic and section views, dimensions, title block, export to SVG/DXF/PDF (our own PDF writer).
  • Fabrication checks: wall thickness, overhangs, manifoldness, printability heat-map, 3MF export.

Nodes & procedural generation

Combines Blender's geometry nodes, Unreal's Blueprints and PCG, and Houdini-style thinking.

One node editor, many graph types

  • Geometry nodes (mesh/point/curve/volume operations on attribute fields).
  • Shader nodes for materials, compiled to the renderer's shading VM.
  • Logic graphs (Blueprint-like) for interactive behaviour in play mode.
  • Compositor nodes for post-processing renders.
  • Fast canvas: thousands of nodes, minimap, reroutes, frames, groups as reusable assets.

Node VM

  • Graphs compile to a compact bytecode, then to a vectorized interpreter where each opcode processes 16 elements (AVX-512).
  • Later: a template JIT that emits x86-64 straight into an mmap'd executable page. We are already writing assembly, so a JIT is a natural fit.
  • Lazy evaluation, per-node caching and incremental re-evaluation when a parameter changes.
  • Fields & attributes: per-vertex, per-face, per-instance, per-point.

PCG & scattering

  • Poisson-disk and blue-noise scattering on surfaces with density maps.
  • Rule-based placement (slope, altitude, exclusion volumes), splines with mesh deformation.
  • Wave Function Collapse and L-systems for tiles, buildings and plants.
  • Terrain: heightfield erosion (hydraulic/thermal) as a parallel job.

Instancing at scale

  • Millions of instances as transform arrays sharing meshlets.
  • Hierarchical LOD and impostors for distant clusters.
  • "Realize instances" turns instances into real geometry on demand.

Sculpt, UV & paint

Organic modeling at scale.

Sculpting

  • Brushes: draw, clay strips, crease, inflate, grab, snake hook, smooth, flatten, pinch, layer
  • Dynamic topology (local subdivide/collapse) and multiresolution levels
  • Masks, face sets, symmetry, stroke stabilizer, tablet pressure curves
  • Target: 50M vertices at 60 fps strokes, using a BVH-partitioned mesh where only touched nodes are updated

UV unwrapping

  • Seams, LSCM and ABF++ unwrap (our own sparse conjugate-gradient solver)
  • Smart projection, packing with rotation (skyline / MaxRects)
  • Distortion heat-map, texel density tools
  • Automatic seam suggestion (also available as an AI tool)

Texture paint & baking

  • Paint in the viewport and in the 2D image editor, with layered textures
  • Bake normal, AO, curvature and ID maps from high-poly to low-poly using the path tracer's BVH
  • Vertex colours and attribute painting
  • Triplanar and decal projection

Animation & simulation

Enough to animate products, characters and mechanisms.

Animation

  • Keyframes on any property, including operator parameters and node inputs (everything is animatable through the property system).
  • Timeline, dope sheet, graph editor with Bézier handles, NLA-style action layers.
  • Armatures with linear-blend and dual-quaternion skinning (AVX-512), automatic weights (heat diffusion), FK/IK (FABRIK + CCD), constraints.
  • Shape keys, drivers (expressions), motion paths, onion skinning.
  • Mechanism animation for CAD: joints driven by parameters (gears, hinges, sliders).

Simulation

  • Rigid bodies: our own physics (GJK/EPA, sequential impulses, sleeping, convex decomposition).
  • Cloth and soft bodies: XPBD solver, self-collision through a spatial hash.
  • Particles and fluids (later): SPH / FLIP for small-scale effects.
  • Results are cached to disk in .bee chunks and can be scrubbed on the timeline.

Engine-grade features

Unreal-inspired capabilities that turn a modeler into a world-building tool.

Virtualized geometry

Meshlet DAG with continuous LOD (Nanite-like), streamed from mmap'd .bee chunks. Billions of source triangles on screen with a bounded memory budget.

World partition

Scenes are split into grid cells streamed by camera distance, so very large maps stay editable within the RAM budget.

Content browser

An asset library with thumbnails, tags, search and dependencies, drag-and-drop into the scene, and "asset packs" stored as content-addressed .bee files.

Play mode

Press F5 to walk or fly through the scene with physics and logic graphs running. Changes made during play can be kept or discarded, as in Unreal's PIE.

Lighting tools

Light probes, a lightmap baker (path-tracer based) and an export-ready glTF scene with KHR extensions for game engines.

Live link

Stream the scene over a socket to a running game engine or another BeeModel (see collaboration), so changes appear instantly.

AI & MCP

An AI-native modeler: BeeModel works as an MCP server, with no TLS stack and no API keys inside the binary.

Key insight. In MCP, the AI host (Claude Code, Claude Desktop or any other MCP client) owns the model and the network connection. BeeModel only has to serve tools over a local transport. That keeps the zero-library rule: we need JSON-RPC and a JSON parser, not TLS or HTTPS. MCP sampling also lets BeeModel's own in-app assistant borrow the host's model.

MCP server design

Transports

  • stdio: beemodel --mcp runs a headless instance (batch generation, CI).
  • Attach to a running app: the GUI listens on $XDG_RUNTIME_DIR/beemodel-<pid>.sock, and beemodel --mcp-bridge forwards stdio to that socket. The agent then edits the scene you are looking at, live.
  • Streamable HTTP on 127.0.0.1 (plain HTTP, local only) for clients that prefer HTTP.
  • JSON-RPC 2.0 with our own streaming JSON parser/writer in assembly. Images are encoded as PNG + base64 by our own encoders.
// Claude Code / Desktop config
{ "mcpServers": {
    "beemodel": { "command": "beemodel",
                  "args": ["--mcp-bridge"] } } }

Capabilities

  • Tools: generated automatically from the operator spine (hundreds), plus a curated, AI-friendly top layer (below).
  • Resources: bee://scene/tree, bee://selection, bee://object/{id}, bee://history, bee://viewport.png, bee://docs/operators. Subscriptions push change notifications.
  • Prompts: "model this from a description", "make this printable", "retopologize for games", "explain this scene".
  • Sampling: lets the in-app assistant panel ask the host's LLM for completions.
  • Elicitation: BeeModel can ask the user structured questions mid-task (e.g. "which units?").

AI features inside the app

Assistant panel

A chat docked like any other editor. It uses MCP sampling through the attached host, or a local OpenAI-compatible endpoint (llama.cpp/Ollama on localhost over plain HTTP). It can see the selection and viewport, and it acts only through operators.

Natural-language command palette

Type "bevel the top edges 2 mm" into F3. Exact operator matches come first; otherwise the request is resolved by AI into a previewed operator sequence.

Text / image → blockout

A description or a reference photo becomes a block-out made of parametric primitives and sketches. Because it is parametric, every number can still be edited afterwards.

Sketch-to-solid

Draw a rough 2D sketch. The AI suggests constraints, dimensions and the likely feature (extrude, revolve, sweep), and you confirm.

Design reviewer

An agent checks printability, manufacturability (draft angles, undercuts), game-readiness (polycount, UV overlap) and topology, and leaves comments pinned in 3D.

Procedural co-pilot

Describe the behaviour you want ("scatter rocks on slopes above 30°") and get a node graph you can inspect and tweak, not an opaque mesh.

Coach mode

The AI watches the operator journal and suggests faster workflows ("you can use loop cut here"), turning BeeModel into a tutor.

Auto-organize

Names objects, builds collections, assigns materials by role and writes scene documentation.

Local smart features (no LLM)

Constraint inference, seam suggestion, retopology flow fields and denoising all run as our own algorithms or tiny AVX-512 int8 networks, so they work offline and instantly.

Trust, safety & control

  • Change sets: every agent session is one named, collapsible group in the undo tree, shown in an "AI activity" panel with a diff and Accept / Reject / Revert-to-here.
  • Permission tiers: read-only · propose (ghost preview) · edit · edit + file I/O. Set per client and per tool, and shown in the status bar.
  • Prompt-injection hygiene: object names, file metadata and script comments are passed as data, never as instructions. Tool results label their sources.
  • Sandboxed scripts: BeeScript has no syscalls. File and network access go only through operators that need a grant.
  • Budgets: limits on operation count, geometry growth (e.g. "max +5M triangles") and wall time per session.
  • Full audit log: who did what (human, agent, script, collaborator), stored in the journal and replayable.
  • Local-first: nothing leaves the machine unless the user's own MCP host sends it.

BeeScript

A small, fast embedded language that AI agents, macros and plugins all share:

  • Expression-oriented syntax that LLMs write reliably (close to Python/Lua), with units as literals (12mm, 45deg).
  • Compiles to the same bytecode VM as the node graphs, so it runs fast and is sandboxed by construction.
  • Records macros: any UI session can be exported as BeeScript.
  • Plugins are BeeScript modules, or external processes that talk the MCP-style protocol, so a crashing plugin cannot take the app down.

UX & workspaces

Fast for experts, discoverable for beginners.

Areas & editors

Blender-style area system: split and join any pane, and each area can host any editor (viewport, outliner, properties, nodes, timeline, UV/image, console, spreadsheet, asset browser, AI). Layouts are saved as workspaces (Modeling, Sculpt, CAD, Shading, Animation, World).

Command palette

F3 / Ctrl+K: fuzzy search over every operator, setting and asset, showing shortcuts and recent commands. Every operator is reachable here because of the operator spine.

Pie & radial menus

Gesture-speed access to modes, pivots, snapping and shading. Hold and flick, no reading required.

Gizmos

Move, rotate and scale gizmos with plane handles, plus CAD manipulators (drag a dimension arrow to change a parameter) and a navigation cube.

Keymaps

Fully remappable, with presets: BeeModel, Blender-like, Maya-like and CAD-like. Conflict detection, and all shortcuts shown in tooltips.

Spreadsheet

Inspect and edit raw attributes (vertices, faces, instances) in a virtualized table. Useful for debugging nodes and for AI explanations.

Themes & accessibility

Theme tokens (the current dark theme becomes the default), a high-contrast mode, UI scale, colour-blind-safe axis colours, full keyboard navigation and reduced motion.

Onboarding

Interactive tutorials driven by the journal: "do this step, I'll check". Sample scenes, plus an empty-state viewport with quick actions.

Multi-monitor

Built for your 3-screen setup: tear-off editors, a dedicated render window, and the node editor on a second screen.

Collaboration & versioning

Git-like history for 3D, and live co-editing.

Versioned scenes

  • Content-addressed chunks plus the operator journal give commits, branches and merges for models.
  • Visual diff: a side-by-side or overlay viewport highlighting added, removed and modified geometry.
  • Three-way merge at entity and feature-tree level, with manual conflict resolution.
  • Can store directly in a git repository as text-free binary that still diffs well, because unchanged chunks are deduplicated.

Live multi-user

  • Operation-based CRDT on top of the journal. Every operator is already a serializable, replayable event.
  • Peer-to-peer over TCP on a LAN, or over an SSH tunnel for remote work (TLS deliberately left to the tunnel).
  • Presence: collaborators' cameras and selections are visible, with "follow user" mode.
  • AI agents join as collaborators with their own cursor and permission tier.

Out-of-the-box ideas

Differentiators that are cheap to build because of the architecture choices above.

Time-travel scrubber

Drag a slider through the whole editing history and watch the model rebuild, because the journal is replayable. Branch from any point.

Live parameter brushing

Hover any number in the feature tree and scrub it while the model updates in real time. Ctrl-drag shows a "variation strip" of 9 alternative values side by side.

Design-space explorer

Mark parameters as variable and give a goal (lightest part with wall ≥ 1.5 mm). An optimizer, or an AI agent, explores the options and shows a gallery of variants.

Explainable geometry

Click any face and see why it exists: which feature, node or operator, and whether a human or an agent created it.

Deterministic everything

Fixed-order parallel reductions and our own math functions give bit-identical results on every machine. Renders and simulations are reproducible, which is great for tests and collaboration.

Instant start

A target of under 50 ms from launch to an interactive viewport, plus a --resident daemon mode that opens new windows in under 5 ms.

Headless BeeModel as a service

The same binary runs as a CLI batch tool or an MCP server in CI: generate parametric parts from a spreadsheet, auto-export LODs, check printability on pull requests.

Physical-world loop

Import photogrammetry and LiDAR point clouds, fit planes and primitives automatically, and export straight to a 3MF slicer profile. Scan → model → print in one tool.

Spectator links

Stream the viewport as a compressed video-like tile stream to a minimal HTML viewer for reviews, with no install needed on the viewer's side.

Self-profiling HUD

Ctrl+Shift+P overlays per-subsystem frame time, memory per arena and job-graph occupancy. Performance becomes visible, which matches the project's priorities.

Procedural "recipes" from meshes

Ask the AI to turn a dumb imported mesh into an editable feature tree or node graph that rebuilds it (inverse procedural modeling).

Tiny-binary bragging rights

A public size budget per release ("v1.0: complete modeler in 1.9 MB") enforced in CI.

Engineering practice

How a codebase of hundreds of thousands of assembly lines stays maintainable.

Code organization

  • One module per subsystem, separate object files, explicit export lists; an internal ABI based on SysV with a documented register contract for hot paths.
  • Macro library: PROC/ENDPROC with automatic save/restore, struct offset generators, OPERATOR/PARAM, SoA table declarations, assertions in debug builds.
  • Dev-time generators (Python) produce tables: operators, schemas, fonts, keymaps, shader opcodes. Their output is committed so the build stays as + ld only.
  • Runtime CPU dispatch: AVX-512 → AVX2 → SSE4.2 code paths, so other machines work too.

Quality

  • Golden-image tests via the fake compositor, using scripted input and pixel diffs with tolerance.
  • Reference implementations in Python/NumPy for math kernels, with differential testing against the assembly version.
  • Fuzzing of every importer and of the MCP/JSON layer (coverage-guided, using a small harness binary).
  • Determinism tests: same journal → identical .bee hash on every run.
  • Benchmarks and memory budgets in CI; a perf-friendly debug build with symbols.
  • MCP conformance tests against real clients (Claude Code) as part of release checks.

Documentation

  • Generated operator reference (also served as an MCP resource).
  • Architecture decision records (ADRs) in Vibecoding/ for every major choice.
  • Annotated "reading guide" for the source: start with main.s, then follow one operator end-to-end.

AI-assisted development

  • Claude Code works on the repo with the fake compositor as its eyes, generating screenshots per change.
  • BeeModel's own MCP server lets agents test the app functionally (create, measure, export) in CI.
  • Strict review checklists for register clobbers, stack alignment and clipping bounds, the classic assembly bugs.

Open questions to decide next

  • Which CAD scope for v1.0: parts only, or parts + assemblies?
