Phase 11 · v0.12.0 · UI & usability

Every feature one click away

BeeModel already has more than 400 operators, from polygon tools to a B-rep kernel, a path tracer and live co-editing. Many of them can only be reached by typing into the console. This plan gives every feature a mouse-and-keyboard UI. It adds a shared widget toolkit, clear text and colours, and conventions that make the app predictable. The console stays as a power tool, but you never need it.

BeeModel · Vibecoding/BeeModel-UI-Plan.html · Companion to the Masterplan, section "UX & workspaces" · Written 2026-10-15 against v0.10.0 + phase 10

Goals

What "done" means for this phase.

No console required

Every feature in the coverage table can be found and used with the mouse and keyboard. That includes file paths, CAD features, paint colours, version control and collaboration. A walkthrough test proves it by building, rendering and saving a scene without typing a single command.

Discoverable

Hovering anything shows what it does and its shortcut. Right-clicking anything shows what you can do with it. Menus show disabled items and say why they are disabled. Each tool's bar hints at its mouse buttons.

Clear and consistent

One widget toolkit, one theme table and three font roles. The same field behaves the same everywhere: drag to scrub, double-click to type, Esc to cancel. Colours carry meaning: amber for active, blue for focus, green for success, red for danger.

Still BeeModel

Hand-written x86-64, no libraries, the 1 MiB binary budget and no allocations per frame. Drawing all the UI chrome stays under 1 ms at 1080p, and the console, palette and MCP keep working unchanged.

The UI today

Inventory of v0.10 plus phase 10: what works, and what holds the UI back.

Solid ground

  • Client-side title bar with window buttons, plus an 8-menu bar with check marks and shortcuts.
  • Blender-style area tree with 13 editor types: split, resize, maximize, close.
  • F3 fuzzy palette over every operator, and a console with history and Tab completion.
  • TrueType text with a bitmap fallback, fractional scaling and layout-aware shortcuts.
  • Interactive editors: viewport, outliner, UV, nodes, timeline, dope sheet, graph and asset browser.
  • Operator spine: each operator has a label, a doc string, a key and flags. This gives one place to hang tooltips, menus and forms.

What holds it back

  • No widget toolkit. Each panel hand-rolls its buttons and hit tests (rp_*, pr_*, mp_*). Hit codes are bitfields routed through HIT_MODS.
  • Fields can't be typed into. Values only scrub sideways. Transforms in Properties are read-only text.
  • Paths are typed. There is no file dialog, no recent files and no unsaved-changes prompt: New and Exit just act.
  • No tooltips, context menus, submenus, scrollbars, tabs, dialogs or icons. The "icons" are 8 px squares.
  • Properties is one clipped column. No tabs and no scrolling, and it ends with debug data (canvas size, area count).
  • The Tools pane never changes. It shows the same 10 buttons in sculpt, paint and sketch modes.
  • One font size and weight, plus hint text spread over the viewport and status bar. The status bar shows the framebuffer size.
  • Preferences is a stub (op_todo). There is no keymap editor, no theme and no UI scale, and the layout is not saved.
Bug found during the survey. Menu item counts are kept by hand in menu_counts (src/ui.s:108) and have drifted from the item lists. As a result, Create › Path / Light / Camera, the Timeline, Dope Sheet and Graph Editor entries in the editor-type menu, the Armature modifier and Mesh › Reset 3D Cursor never appear. U1 fixes this by deriving the counts from the lists.

Design language

Every colour and size has one meaning and one definition, the theme table.

Colour roles

TokenDark (default)Meaning
bg / panel / raised1b1d22 · 2a2e36 · 363b45Window, panel and button surfaces, each step lighter
field1d2025Anything you can type into or scrub (fields always look darker than the panel)
text / text-2 / text-offe4e6ea · 9aa1ad · 5f6672Primary text (≥ 7:1 contrast), labels (≥ 4.5:1), disabled
accentf2b134Active: the active tool, tab, object and workspace, and the primary button
focus61afefKeyboard focus ring and text caret. Never used for selection.
ok / warn / danger4cb86a · e0a030 · e5484dToasts, status chips, feature health. Red also marks destructive buttons (Delete, Discard).
axis-x / y / zViewport axes and XYZ field tints. A colour-blind preset swaps in orange, blue and violet.

Built-in themes: Dark (today's look, cleaned up), Light and High contrast (pure black and white, 2 px focus rings, thicker splitters). Themes are tables in memory, so switching takes effect on the next frame.

Type

  • Body 15 px: labels, menus, fields
  • Small 13 px: hints, units, status bar
  • Heading 16 px semibold: panel and dialog titles
  • Mono 14 px: console, code and numbers in tables

Spacing

  • 4 px grid; rows are 24 px, and 28 px for tool buttons
  • 4 px corner radius on fields, 6 px on popups
  • Popups get a 1 px border and a soft shadow
  • Every size is multiplied by the UI scale preference

Icons

  • About 100 icons at 16 px, stored as an alpha mask and tinted by role
  • Generated from vector source by tools/genicons.py, like the bitmap font
  • Every icon button has a text tooltip

Mouse & keyboard rules

The conventions every widget and editor follows. They are written down so tests can check them.

Mouse

HoverHighlight, a hand cursor on clickables, and a tooltip after 500 ms (name, shortcut, doc, and why it is disabled when it is)
LMB clickSelect or activate. Shift extends, Ctrl toggles.
LMB drag on a fieldScrub. Ctrl snaps to steps, Shift is fine (×0.1).
Double-click a field or nameType a value or rename. Expressions and units work: 2*pi, 25 mm.
RMBContext menu, everywhere. It still cancels while a modal tool runs.
MMB / wheelViewport pan / zoom (unchanged). Over a panel, the wheel scrolls; Ctrl+wheel steps the field under the cursor.
Drag and dropOutliner rows to reparent, assets into the viewport, area header onto another area to swap

Keyboard

EscCloses or cancels the topmost thing: tooltip, menu, dialog, field edit, modal tool
EnterConfirms a dialog or field (Enter in the viewport still focuses the console)
Tab / Shift+TabNext / previous field inside a panel or dialog (in the viewport, Tab still toggles edit mode)
F1 F2 F3Shortcut overlay · rename the active item · command palette
F6 / F10 / Alt+letterCycle area focus · open the menu bar · open a menu by its underlined letter
Arrows, Home/EndMove in menus, lists, the outliner and the file browser
I over a fieldInsert a keyframe on that property; Alt+I removes it
Ctrl+C / Ctrl+V over a fieldCopy / paste the value through the Wayland clipboard
Compatibility. Today's shortcuts keep working. Where a new rule conflicts (RMB, Tab inside panels), the new behaviour applies only over UI chrome, never inside the viewport. The Preferences keymap editor lets users change any of it.

Architecture

How the toolkit fits the existing modules without a rewrite.

Immediate mode, stable ids

Panels keep drawing in immediate mode, as they do today. Each widget call looks like wg_number(id, rect, ptr, desc): it draws, records its rect in a per-frame widget list, and returns "changed". Hit testing reads the previous frame's list, so the per-module *_hit functions and bitfield hit codes go away. The id is a hash of the panel id and the field index, which stays stable across frames.

Operators stay the spine

Buttons, menu items, context menus and form OK buttons all go through run_op, so undo, macros, MCP, co-editing and the journal see every UI action unchanged. Field edits use the same property paths as set() and anim.key, which is why "keyframe any field" is cheap.

Parameter descriptors

A new OPARAM macro next to OPERATOR declares each argument (type, default, range, unit, enum list, file filter). Three consumers share it: the form generator (U7), console Tab completion and the MCP tool schema, which today is hand-written per tool.

Layers on screen

The draw order is areas, then area overlays (headers, tool bar, toasts), then menus and popovers, then dialogs, then tooltips. Input runs top down through the same stack, so the long ui_button if-chain becomes "topmost layer that wants it".

Testing

The fake compositor already drives the app. This phase makes those tests robust to layout changes.

  • Click by id. ui_tree (MCP) returns every widget's id, rect and value, and fakewl.click_id("props.object.loc.x") finds the widget from it. New tests never hard-code coordinates, and old coordinate-based tests are migrated as their panels change.
  • Goldens. The five bitmap-font goldens are regenerated deliberately at U2, U10 and U11. Each widget also gets small goldens in all three themes.
  • Contrast check. A test renders each theme and checks the text against background pairs listed in the theme table.
  • Console-free test. Each Stage C issue adds a test that uses its feature with clicks and keys only. U27 chains them into one walkthrough.
  • Performance. A test measures UI draw time with every panel open, and checks there are no frame-arena leaks while hovering and tooltips are shown.

Risks

  • Test churn. 67 pixel asserts and 76 fixed-coordinate clicks. Mitigation: ui_tree first, then migrate tests as each panel changes.
  • Binary budget. Forms come from descriptors rather than hand-written panels, and icons are 1-byte alpha masks.
  • Shortcut conflicts. RMB and Tab change meaning only over UI chrome, and the keymap editor exposes everything.
  • Scope. 27 issues. Stage C items each ship separately; if time runs short, the release can go out after any of them.
